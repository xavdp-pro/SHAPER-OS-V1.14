# V1.14 — Operational continuity across engines

> **Intent Classification**: GENERIC INTENT (Universal / Parameterized Blueprint)
> **Status:** development work, opened 2026-09-05. Not a release or a cold-test verdict.

## Objective

- Let an authorised agent enter an assigned universe, understand its mission,
  use the available tools, produce externally checkable work and hand it over.
- Preserve the human's ability to shape the system. The kernel informs design;
  the running agent receives the context relevant to its actual mandate.
- Qualify an engine together with its tool harness and environment, on measured
  tasks. A model name or a successful chat response proves no operating capability.
- Keep the base generic; product-specific work remains in its own universe.
- Make interruptions, missing capabilities and unverified results visible.
- Prepare a frozen candidate for a later multi-engine cold campaign.

## Starting point and release identity

The starting commit is `0ef7b8a` on the V1.13 history. Development uses branch

lot is assembled; this is inherited metadata, not a claim that the modified

A base or catalogue's root `package.json` declares its release. A checkout's
directory name does not change that release. Historical proofs retain the
version and commit they actually measured. Release preparation must align the
package metadata, manifests and active entry documents before a candidate tag.

## Subsequent work, in dependency order

1. **Context and continuity.** Carry current decisions and their reasons, locate
   durable job records and artefacts, and reconcile in-flight work before retry.
   A conversation reset does not undo external effects.
2. **Observed state and recovery.** Join the existing governor, maker and
   supervisor responsibilities; verify fresh observations and bounded remedies.
3. **Proposal execution integration.** Bind authenticated authority to stored
   proposals, retire superseded proposals, and deduplicate transactionally in
   the caller that owns the effects. A digest is not authentication.
4. **A useful product journey.** Prove one complete workflow in a product
   universe and its transfer to another operator. This remains product work.
5. **Release qualification.** Run the common contract against the engines and
   harnesses measured as available, then publish the actual compatibility scope.

## Validation of this development lot

Observed locally on 2026-09-05 with Node 22.23.2: `npm test` passed **538 tests
in 114 suites**, with no failures or skips. `npm run verify` passed all **8
checks**. The initial regression run failed 10 proposal/version cases on the
unpatched implementations; the four context-delivery cases also failed before
their fixes. The bridge transport test first exposed a missing child cwd, then
proved that only the request, without its context, reached the backend.

The transport test uses the real bridge process and local HTTP with a protocol
recorder. It inspects outgoing request contents and refusals; it does not run a
model or establish model/CLI compatibility. No live SHAPER deployment, cold
image build, model availability measurement, or multi-engine run has yet been
performed for V1.14. Fresh-LXC source verification also passed all 538 tests
without skips and all 8 checks on Debian 13 with Node 20.19.2, as an
unprivileged test user. The dedicated test instance was deleted; existing
instance names and states match the pre-test inventory. See the
[source verification record](V1.14-SOURCE-VERIFICATION.md) for scope and limits.

## Does 1.14 need its own catalogue? Measured, 7 September 2026

`SHAPER-OS-BRICKS-V1.14` does not exist. Before cutting one, the question was
whether anything in 1.14 requires it. Measured rather than assumed:

**The base and the catalogue hold disjoint sets.** Not one package is in both.
The base carries the kernel every universe has — runtime, auth, bridges,
governor, logger, maestro, opencode-server, proposal, queue, supervisor,
universe, vault, verify. The catalogue carries what a universe may *add* —
`pkg-db`, `pkg-fleet-dns`, `pkg-ged-engine`, `pkg-mail-agent`, `pkg-rag`, and
the bricks `ged`, `helm`, `mariadb`, `pipeline`, `qdrant`, `waf`.

**Nothing in 1.14 so far touches a contract the catalogue depends on.** The one
contract that changed is task-context resolution (`pkg-maestro/task-paths.js`).
Two apparent hits in the catalogue are not it:

* `brick-helm`'s `contextPath` is a Helm session file, unrelated to the maestro
  task contract — same word, different thing.
* `univ-demo` declares `./tasks/task-schedule.json` and its deploy script sets
  `TASKS_FILE=/data/univ/tasks/task-schedule.json`. That is the `tasks/`
  subdirectory layout, which the new resolution still serves — it is the second
  candidate it tries, which is exactly the behaviour the old code had. Backward
  compatible by construction, and covered by a test built on that layout.

**Therefore**: cut a 1.14 catalogue when a catalogue brick actually changes, or
when the base breaks a contract one of them uses. Not to align a number. The
fleet map keeps naming the 1.13 pair until both halves of 1.14 exist, because a
map that says *base 1.14, catalogue 1.13* would describe an ecosystem that is
not there.

### The question worth spending a large model's credit on

Not "write the 1.14 catalogue spec" — that presumes the answer measured above.
The unanswered question is the boundary itself:

> The base has grown. `pkg-proposal`, the four bridges and `pkg-opencode-server`
> are in the kernel every universe carries, yet a universe that never talks to
> an agent carries them anyway. The catalogue exists precisely for what a
> universe may add. **Where does the line between base and catalogue actually
> fall today, and which of the base's current packages are on the wrong side
> of it?**

That is one hard question, bounded, and answerable by reading — the shape §8 of
the inter-agent protocol reserves for the largest model.
