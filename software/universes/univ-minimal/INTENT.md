# univ-minimal

> **Intent Classification**: SPECIFIC INTENT (Universe: `univ-minimal`)

## Objective

The minimal composition of a SHAPER universe, materialised: **Vault, Logger,
Queue and Maestro**, each a functional Podman that holds its application and
its own MariaDB server (Rules 4 and 26, the Turbinobash method: one application
account per server). No cognition adapter, no catalogue brick, no domain, no
public door. It is the floor every other universe of the current construction
model stands on; the reference universe adds the OpenCode bridge on top of it
(profile `agent`).

Maestro is present and idle: with no declared schedule it submits nothing.

Every state change of Vault, Queue and Maestro commits its evidence to the
unit's own outbox in the same transaction, and each unit delivers it to Logger
under a short-lived credential Vault signs for it ([identity](#identity)) —
asked for only when its outbox owes a row. Logger, Queue and Maestro accept
and serve nothing but a minimal health without such a credential, each route
under its own scope. Vault leaves evidence of every secret read before the
value leaves, and of every refusal, bounded.

## Exact runtime — four units, four containers, eight processes

| Unit | Container | Application account | MariaDB server account | Socket (inside the container) |
| :--- | :--- | :--- | :--- | :--- |
| Vault | `<universe>-ctr-vault` :8610 | `vault` / 10610 | `mysql` / 10611 | `/run/vault/mysqld.sock` |
| Logger | `<universe>-ctr-logger` :8620 | `logger` / 10620 | `mysql` / 10621 | `/run/logger/mysqld.sock` |
| Queue | `<universe>-ctr-queue` :8640 | `queue` / 10640 | `mysql` / 10641 | `/run/queue/mysqld.sock` |
| Maestro | `<universe>-ctr-maestro` :8630 | `maestro` / 10630 | `mysql` / 10631 | `/run/maestro/mysqld.sock` |

Each container runs `tini`, the unit supervisor (root, the container's
administrative path, [`runtime/unit-mariadb`](../../runtime/unit-mariadb/INTENT.md)),
and its two children: `mariadbd` as the engine account and the application as
the unit account. Application containers use the universe's host network and
bind `127.0.0.1` only; MariaDB has no network at all.

<a id="private-mariadb"></a>
## Each unit's database is its own, inside the unit

What the unit image does at every start, and what `deploy/proof.sh` checks from
outside the unit:

1. **One name everywhere.** The functional slug is the Linux account inside the
   unit (fixed uid, home `/apps/<slug>`), the MariaDB account and the database.
2. **Two processes, one container.** The MariaDB server runs in the unit's own
   container, as `mysql` with a fixed uid distinct per unit, `--skip-networking`,
   socket `/run/<slug>/mysqld.sock` in a directory owned by `mysql`, group
   `<slug>`, mode `0750`, rebuilt at every start and mounted nowhere. There is
   no database container beside the unit; one found is refused.
3. **Two paths, never mixed.** The application account holds `SELECT, INSERT,
   UPDATE, DELETE` on its own database and nothing else. Root authenticates by
   `unix_socket` as OS root inside the container only; at first birth every
   other account the engine created is removed, and at every start a retained
   root that accepts anything but `unix_socket`, or any unexpected principal,
   refuses the start before any grant or schema statement (exit 8). The schema
   is the unit image's own, applied by root into an empty database only; a
   retained database must carry exactly the declared schema version (exit 7).
4. **The password is a private file, generated once.** `/apps/<slug>/etc/mysql/localhost/passwd`,
   64 hex characters, `0600`, owned by the unit's account, in a directory owned
   by root. It is generated by the unit when its datadir is born, travels on
   standard input or in a root-only option file and never on a command line,
   and must open the retained account at every start (exit 9): recreation
   never rotates it silently.
5. **The application cannot reach the server's files.** The datadir, the
   socket directory, the password directory, the schema, the runtime and the
   MariaDB option files are not writable by the unit's account, nor is any of
   their ancestors; the supervisor refuses to start otherwise, and the proof
   checks it with `access(2)` as the unit's uid.
6. **Born with the function.** The database, the account and the schema exist
   before the application starts; readiness (`unit-ready`, the container's
   health command) is gated on the MariaDB process the supervisor started. The
   durable state of every unit is in its database — no JSON, JSONL or SQLite
   store serves in this universe.
7. **Persistent and restorable.** The volumes each unit declares
   (`database.volumes` in the manifest), on the universe container:
   `/apps/<slug>/etc/mysql` (the password), `/apps/<slug>/sav` (the datadir
   `sav/mariadb`, owned by the unit's engine uid, and `sav/dumps`), and
   `/apps/<slug>/log` for Vault, Logger and Queue. Maestro has no log volume:
   its durable path writes no local file, its evidence is an outbox row until
   Logger receipts it. Ownership is set on single directories only, never
   recursively.

The Vault master key is `/apps/vault/etc/vault/master.key` (`0400`, owned by
`vault`, mounted read-only as a single file). It is generated only when the
Vault is born; a Vault whose datadir exists without its key is a halt, never a
new key; `etc/vault/` itself is never mounted. The Vault API token is a secret
the unit consumes: it lives in the secrets store and reaches Vault as a file
([secret files](#secret-files)).

<a id="secret-files"></a>
## Secrets reach a unit as private files, never through its environment

SOL-DECISIONS-2 §M (Rules 0J, 4 and 12). A value in a container's environment
sits in `podman inspect`, in the initial environment of PID 1 (`tini`, which
the supervisor cannot clean) and in every process that inherits it; a file
descriptor hand-over fixes the children, not the first two. So:

- **The parent's store.** `SHAPER_SECRETS_ROOT` (default
  `<SHAPER_APPS_ROOT>/.state/secrets`) is root's alone, `0700`, and no
  ancestor of it can be replaced by another account — every existing
  component root-owned, none writable by group or others unless sticky
  (`path_protected`; `podman-up.sh` halts otherwise). One root `0700`
  directory per unit holds its sources, each a root `0600` file named after
  the variable: `<store>/<unit>/<NAME>`. The declaration of which unit
  consumes which secret is `secrets_of` in `deploy/unit-probes.sh`, shared
  with the proofs: today Vault's `VAULT_TOKEN` (the generic secret API's
  bearer, generated here at birth). A source that is absent or empty is a
  halt (Rule 0J), never a unit started hoping.
- **The unit's copy.** `<store>/<unit>/mount/<NAME>`, owned by the unit's
  account, `0400`, replaced only when it differs from the source (a kept
  container keeps what it reads; a changed value changes the unit's run
  specification and recreates it). It is mounted **alone, read-only** at
  `/run/secrets/<NAME>`, and the unit receives only the reference
  `<NAME>_FILE=/run/secrets/<NAME>`. The store and its directories are never
  mounted; nothing is sourced or exported into a process environment.
- **The application reads the file itself** (pkg-auth
  [`secret-file.js`](../../packages/pkg-auth/INTENT.md#secret-files)): a
  regular file of its own account with no group or other bit, read once into
  memory. On MariaDB a value in the environment is refused
  (`SECRET_IN_ENVIRONMENT`), and so is a secret given both ways.
- **The unit runtime refuses** to start a container whose environment gives
  a secret-shaped variable (`*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_PWD`,
  `*_API_KEY`, `*_MASTER_KEY`, …) a value: exit 13, by name, never by value
  (runtime/unit-mariadb). A plain `unset` would not qualify.
- **The settings file** (`cfg-univ-minimal.env`) carries parameters only,
  read by the base's declarative reader ([settings](#settings)): a secret
  given a value there, or inherited from the caller, is refused by name before
  anything runs.
- **A universe-wide store.** A universe that holds more units than the base
  (the seven-unit Clinic kit) names one store for all of them,
  `SHAPER_SECRETS_ROOT=<universe>/.state/secrets`, while `SHAPER_APPS_ROOT`
  keeps the base units' volumes where they are. Its other consumers' directories
  follow the same layout — root `0700` directories, root `0600` sources,
  `<consumer>/mount/<NAME>` the consumer's `0400` copy — because the base's
  proof holds the whole store to it (`secrets-store`) and looks for every
  source's value in the base units' processes. The base writes only under its
  own units' directories (`vault/` today) and creates the store's root when it
  is absent; a store inside a unit's own directory is refused, since that
  directory's volumes are mounted into the unit. A universe that names the
  store after its birth keeps its values: `podman-up.sh` moves each base
  unit's source from the earlier default store (`<apps root>/.state/secrets`)
  into the named one, atomically and under the parent lock, removes an earlier
  copy of the same value, refuses two different values (a human's decision),
  and recreates the unit, whose mount changed.

Unchanged, by decision: the Vault master key keeps its own file
(`etc/vault/master.key`), the bootstraps theirs (`etc/identity/bootstrap`),
the MariaDB passwords their canonical place
(`/apps/<slug>/etc/mysql/localhost/passwd`). A universe born before the store
kept the API token at `etc/vault/api-token`: `podman-up.sh` moves it into the
store, the same value, so the running Vault and the proof keep agreeing. Root
keeps its declared administrative access to every file; that limit is
explicit, not closed. A later realization with podman secrets uses
`type=mount` with an explicit uid and mode, never `type=env`.

<a id="settings"></a>
## Settings: read, never executed

SOL-DECISIONS-4 §5 (Rules 0B, 0J and 29; Boot contract §7). Every script of
`deploy/` that reads its settings — `podman-up.sh`, `proof.sh`,
`lifecycle-drill.sh`, `restore-drill.sh`, `renew-bootstraps.sh`,
`install-renewal-timer.sh`, and a template universe's `deploy/lib.sh` from
`base/deploy/` — reads them with one declarative reader,
[`deploy/settings.sh`](deploy/settings.sh), before it changes anything. No
settings file is `source`d, evaluated or expanded.

- **Which file.** `ENV_FILE` when named: a regular file, or `/dev/null` for
  none; a named file that does not exist is a halt, never a fall back to
  another one. Otherwise `cfg-univ-minimal.env` beside `deploy/` when it
  exists.
- **A line** is a blank, a `#` comment, or `KEY=value` (an optional `export`
  before it). The value is a bare word, `'…'` or `"…"` (with `\$`, `` \` ``,
  `\"`, `\\` escapes), followed by nothing or by whitespace and a comment —
  the forms an earlier file used and `source` read, now read without being run.
- **Refused, by key and line number, never by value or text:** a key outside
  the catalogue; a secret given a value (one of the base's secrets —
  `VAULT_TOKEN`, `VAULT_MASTER_KEY`, `UNIT_BOOTSTRAP_TOKEN` — or any
  secret-shaped name); `$`, backquotes, `;`, `|`, `&`, `<`, `>`, parentheses,
  a backslash or a second word outside quotes, an expansion or a backquote
  inside double quotes; a key given twice; a run knob in the file; a value not
  of its parameter's form. An empty line of one of the base's secrets, and
  `VAULT_TOKEN_FILE=/run/secrets/VAULT_TOKEN`, are what an earlier file kept
  and are accepted, with no effect.
- **The inherited environment** is held to the same catalogue: a parameter
  inherited from the caller must have its form and may not contradict the
  file; one of the base's secrets, or a secret-shaped name in the base's
  namespaces (`SHAPER_`, `VAULT_`, `UNIT_`, `MARIADB_`, `MYSQL_`, …), holding a
  value is refused; so is an unknown `SHAPER_*` or `RESTORE_DUMP_*` name, a
  variable that changes how a shell or loader behaves (`BASH_ENV`,
  `SHELLOPTS`, `LD_PRELOAD`, …), an exported shell function and an entry whose
  name no shell can hold.
- **The explicit environment.** The values become variables of the script,
  none exported, and its exported environment is reduced to `PATH`, `HOME`,
  the locale, `TZ`, `TERM`, `TMPDIR`, `USER`, `LOGNAME`, `XDG_RUNTIME_DIR` and
  podman's `CONTAINERS_*CONF`: podman, conmon and every other command receive
  that and their arguments, nothing else. A base script run by another
  (`lifecycle-drill.sh` → `podman-up.sh`, `renew-bootstraps.sh`; a template's
  `deploy/base.sh`) receives an environment built explicitly (`env -i`):
  `ENV_FILE`, the settings that hold a value, and the run knobs it is meant to
  have.

The catalogue (`SHAPER_SETTINGS_CATALOGUE`; every form accepts the empty
value, which leaves the default):

| Parameter | Where | Form |
| :--- | :--- | :--- |
| `SHAPER_UNIVERSE` | file or inherited | instance slug `univ-…` |
| `SHAPER_APPS_ROOT` | file or inherited | absolute path |
| `SHAPER_SECRETS_ROOT` | file or inherited | absolute path |
| `SHAPER_REGISTRY` | file or inherited | registry `host[:port][/path]` |
| `SHAPER_IMAGE_TAG` | file or inherited | image tag |
| `SHAPER_UNIVERSE_ID` | file or inherited | lowercase UUID |
| `PROOF_STATE_DIR` | file or inherited | absolute path |
| `RENEWAL_EXTRA_IDENTITIES` | file or inherited | slugs separated by spaces |
| `RENEWAL_ALERT_UNIT` | file or inherited | one `….service` |
| `PARENT_LOCK_WAIT_SECONDS` | file or inherited | whole number |
| `PODMAN_UP_RECREATE` | inherited only (one run) | slugs separated by spaces |
| `RENEW_WITHIN_SECONDS`, `RENEW_EXTEND_SECONDS` | inherited only | whole number |
| `DRILL_PORT_SHIFT` | inherited only | whole number |
| `SYSTEMD_DIR` | inherited only | absolute path |
| `NO_SYSTEMCTL` | inherited only | `0` or `1` |
| `RESTORE_DUMP_<slug>` | inherited only | `/apps/<slug>/sav/restore/<file>.sql`, a declared unit |

A universe that adds units of its own (the Clinic kit) keeps the base's file
to this catalogue and reads its own parameters with its own catalogue; the
grammar and the refusals above are the ones the kit's reader aligns with.

<a id="identity"></a>
## Unit identities: the parent's registration and the birth order

The universe identity is a lowercase UUID, `/apps/vault/etc/vault/universe-id`,
generated once beside the master key (or named by `SHAPER_UNIVERSE_ID` at
birth). With the key it derives Vault's Ed25519 signing key, and it is part of
every Maestro occurrence id: a Vault or Maestro database without it is a halt —
unless `SHAPER_UNIVERSE_ID` names the known identity, which is recorded again —
never a new identity, and a `SHAPER_UNIVERSE_ID` that differs from the
recorded one is refused.

`deploy/podman-up.sh` is the parent of
[`pkg-vault/unit-registration.js`](../../packages/pkg-vault/INTENT.md#parent-registration),
which it runs from the Vault image itself (no network, no capability).

**Kept or recreated** (DECISIONS-20261011 §B). A unit is recreated only when it
must be: no container, a container not running, another image or run
specification — the digest of its image id, the fixed options and its
arguments, all but its incarnation, carried by the container as
`org.shaper.run-spec` — an incarnation that is not the one the parent
recorded, an identity Vault no longer holds live, or an explicit
`--recreate <slug>`. Anything else is kept, with its incarnation.
`--preflight` checks everything and says, unit by unit, what a run would keep
or recreate, writing, registering and starting nothing. `--recreate all`
recreates every unit and renews the proof's identity; `--recreate proof`
renews the proof's identity alone.

At every run:

1. **The pin.** Vault's public key, derived from the master key and the
   universe UUID — never read from a running Vault — written root-owned `0644`
   to `/apps/<slug>/etc/identity/vault-signing.pub` for Logger, Queue and
   Maestro (`UNIT_AUTH_PUBLIC_KEY_FILE`).
2. **The registrations.** A new random incarnation `<slug>-<16 hex>` for each
   *recreated* unit that owes evidence to Logger — `vault`, `queue`, `maestro`
   — with its declared grants (`grants_of`: `logger=logger:ingest` for each,
   and Maestro's `queue=queue:enqueue`, `queue=queue:read`), and one for the
   proof's identity `proof` when it holds none live (`PROOF_GRANTS`:
   `logger:ingest`, `logger:read:own`, `queue:enqueue`, `queue:read`,
   `queue:claim`, `queue:attempt`, `maestro:read`, `maestro:admin` — each right
   explicit, no Vault administration). Each bootstrap is a new file owned by
   its unit's account, `0600`, at `/apps/<slug>/etc/identity/bootstrap`
   (`UNIT_BOOTSTRAP_TOKEN_FILE`); the proof's is root-only under
   `PROOF_STATE_DIR` (`/var/lib/univ-proof/<universe>/identity/`). The
   statements root applies carry each bootstrap's SHA-256, never its value;
   they wait in `/apps/vault/etc/vault/registration/registration.sql`
   (root-only). Vault's bootstrap is put in place at once (its new container
   reads it at start); those of Queue, Maestro and the proof wait in that
   root-only directory until Vault holds their digests, so a run that stops
   halfway leaves the running units and the proof with identities that work.
   The holders, the pinned units and the grants are declared once, in
   `deploy/unit-probes.sh`, for `podman-up.sh` and the proofs alike.

Then the units start (or are kept) in `bootOrder` — Vault alone first. As soon
as Vault is ready, the kept holders' and the proof's identities are checked
live in Vault (recorded incarnation, epoch, grants and bootstrap digest, not
revoked, unexpired; the bootstrap file in place the one recorded) — a holder
that fails is recreated — and root applies the registrations to Vault's
database through its socket (`mariadb -uroot vault < registration.sql`), reads
them back, delivers the staged bootstraps and records each identity root-only
in `/apps/vault/etc/vault/registration/records/<unit>.json` (unit,
incarnation, epoch, grants, bootstrap digest — never the bootstrap); only then do
Logger, Queue and Maestro start, each in its own layer. Every unit receives
`SHAPER_UNIVERSE_ID` and its `etc/identity/` read-only; a unit that holds a
credential also receives `SHAPER_UNIT_INCARNATION` and
`UNIT_BOOTSTRAP_TOKEN_FILE`, one that verifies receives `VAULT_URL` and the
pin. Vault and the units that owe evidence receive `LOGGER_URL`.

A recreation is a new incarnation: the epoch of the recreated unit's identity
moves, and the credentials of the container it replaces stop being current at
once. A re-run that recreates nothing registers nothing: incarnations and
epochs stay. A bootstrap expires after 30 days (pkg-vault's default); the
parent's daily renewal extends a live incarnation's bootstrap before it
expires, without restarting anything ([renewal](#renewal)).

<a id="renewal"></a>
## The parent's daily bootstrap renewal

DECISIONS-20261011 §D, made selective by SOL decision L (11 October 2026),
which replaces its all-or-nothing halt. `deploy/install-renewal-timer.sh`
(once, as root, after `podman-up.sh`) installs
`<universe>-bootstrap-renewal.timer` and its service in the universe
container, rendered from `systemd/`: daily, and at the next boot after a
missed day. Each run is `deploy/renew-bootstraps.sh`, the parent acting
through Vault's local administrative path — not a Maestro task, not a unit's
own act:

1. the identities are inventoried from the composition: every credential
   holder the manifest declares (`HOLDS_CREDENTIAL`) and the proof's identity,
   the identities an installing universe declares in
   `RENEWAL_EXTRA_IDENTITIES` (space-separated slugs, its variables file: the
   units it registers beyond the base's), then any record of a unit outside
   them (`unexpected`) — so a record file that disappeared is reported
   `missing`, never skipped;
2. `pkg-vault/unit-registration.js renew`, from the running Vault's image (no
   network, no capability), turns them and the parent's records
   (`registration/records/*.json`, mounted read-only) into one transaction;
3. root applies it through Vault's socket. Each identity's row is locked and
   checked — universe, unit, incarnation, epoch, grants, recorded bootstrap
   digest, not revoked, not expired. Each consistent one expiring within 7
   days gets 30 days more **from its current expiry**, with its
   `UNIT_BOOTSTRAP_RENEWED` proof in the same transaction. A missing,
   expired, revoked, inconsistent or unexpected one stays exactly as it is,
   and `UNIT_BOOTSTRAP_RENEWAL_PARTIAL` (level `ERROR`, every identity's
   state, the same run id as the proofs) is committed with them. Any SQL or
   proof failure rolls the whole transaction back.

The run prints one line per identity (`renewed`, `current`, `missing`,
`expired`, `revoked`, `inconsistent` with the differing fields, `unexpected`)
and its outcome, also written root-only and without a secret to
`registration/renewal/last.json`. Its exit status is what the timer's unit
shows:

| Exit | Outcome | Meaning |
| :--- | :--- | :--- |
| 0 | `complete` | every identity renewed or current |
| 1 | `halted` | nothing renewed by this run: the universe identity (no UUID, or no identity of it in Vault — then `UNIT_BOOTSTRAP_RENEWAL_HALTED` is committed), an input (a record that is not a private, well-formed file of its unit) or root's authority over Vault (Vault not running, the statement refused) could not be verified, or the transaction failed and rolled back |
| 2 | `partial` | the consistent identities are renewed and listed; the blocked ones are unchanged and expire unless the operator acts |
| 3 | `unknown` | root's acknowledgement was lost: the proofs of the run were re-read and say what was committed, or could not be read |

Before root applies a run, its id is kept in `registration/renewal/unsettled`.
An acknowledgement that does not come back — a client failure, an incomplete
answer — is settled from Vault's outbox (`unit-registration.js readback`: the
run's `UNIT_BOOTSTRAP_RENEWED` rows and its alert) before anything else; when
the proofs cannot be read, the marker stays and the next run settles it
first, or halts without repeating anything. A repeat is safe in any case: a
renewed identity is 30 days away from expiring, so no longer due.

Every non-zero exit fails the service. The alert reaches a human through the
universe's watcher, which reports a failed renewal unit on its declared human
channel (Rule 27); with `RENEWAL_ALERT_UNIT=<the watcher's service>` at
install time, the unit's `OnFailure=` starts the watcher at once. That path
depends neither on Vault's relay nor on Logger: Logger receives the same
events through the relay as evidence, never as the alert.

It creates no identity, changes no incarnation, epoch or grant, never revives
a revoked identity, restarts nothing, and prints no token: records and
statements carry digests only. `RENEW_WITHIN_SECONDS` and
`RENEW_EXTEND_SECONDS` exist to drill it (`lifecycle-drill.sh` uses a window
covering every recorded identity, 40 days at least), never in the timer. One parent at a time: `podman-up.sh` and the
renewal hold `/apps/vault/etc/vault/parent.lock` (`flock`, closed to every
podman child) while they read or change identities and records. A universe
configured by `ENV_FILE` gets a service that names the same file. Both
renewal scripts read that file with the reader `podman-up.sh` uses
([settings](#settings)) — never executed, only the base's parameters, no
secret: the timer runs the renewal directly, through no guarded wrapper, and a
refusal is a halt (exit 1) the watcher reports. `install-renewal-timer.sh`
also refuses a setting its own run took from the environment rather than from
the file the service will read. The renewal itself consumes no secret file: it reaches
Vault's database as root through the socket inside the unit, and its tool
runs from Vault's image with no secret in its environment.

<a id="extra-identities"></a>
## Identities an installing universe adds (SOL decision N)

A universe that installs this base and runs units of its own (the Clinic kit:
`brick-ipbx`, `brick-voice`, `brick-tools`) has them hold Vault-signed
credentials through the same parent, with `deploy/extra-identity.sh` — the
shared interface is [pkg-auth PROFILES.md](../../packages/pkg-auth/PROFILES.md):

| Command | Does |
| :--- | :--- |
| `pin --to <file>` | installs the key `podman-up.sh` pinned (the parent's derivation), root's, 0644: the unit's `UNIT_AUTH_PUBLIC_KEY_FILE` |
| `register --unit <slug> --bootstrap <file> --owner <uid> (--profile <aud>/<profile>=<scope> \| --grant <aud>=<scope>)…` | a new incarnation `<slug>-<16 hex>` with exactly these rights; the bootstrap is delivered only once root has applied the registration through Vault's socket and read it back, then recorded in `registration/records/` like the base's. Standard output: the incarnation alone |
| `live --unit <slug> --bootstrap <file>` | exit 0 and the incarnation when Vault holds the identity exactly as recorded and the file is the recorded bootstrap |
| `revoke --unit <slug>` | revokes it in one transaction with `UNIT_IDENTITY_REVOKED`; only a new `register` brings it back |

The unit must be declared in `RENEWAL_EXTRA_IDENTITIES` — what the daily
renewal inventories is exactly what may be registered — and never be a base
unit or `proof`. The bootstrap's directory must exist and be changeable by
root alone. It holds the parent lock like `podman-up.sh` and the renewal, runs
the registration tool from the running Vault's image with no network and no
capability, and prints no bootstrap, token or key. A new `register` bumps the
epoch: the previous incarnation's credentials stop at once, so the installing
universe registers right before it recreates the unit's container with
`SHAPER_UNIT_INCARNATION` set to the printed incarnation. A revoked identity is
reported `revoked` by the renewal until it is registered again. Proof: the
rehearsal's decision N test (registration, refusals, per-profile credentials,
renewal, new incarnation, revocation, no secret in the output).

<a id="host"></a>
## What the universe container must provide

Checked by `deploy/podman-up.sh` before anything starts, or recorded here as
measured on terrain:

- `podman`, `nftables` (Rule 11), `jq`, `openssl`, `curl`, `iproute2` (`ss`);
- `podman-restart.service` enabled, so the `--restart=always` containers come
  back after the universe container restarts;
- on a Proxmox **unprivileged** LXC (`proxmox` family): `nesting=1,keyctl=1`,
  **and `/dev/net/tun` passed to the container** (`pct set <id> --dev0
  /dev/net/tun,mode=0666`, then a restart). Without it, every `RUN` step of a
  `podman build` fails inside the container (`pasta … /dev/net/tun: No such
  file or directory`), while `podman run` of a prebuilt image works — a host
  that only runs containers looks fit and is not;
- building a unit image needs outbound access to the Alpine package
  repositories of the Node image's release: each image installs its own
  MariaDB server.

<a id="proof"></a>
## What the proof shows, and what it does not

`deploy/proof.sh` exits 0 only when every unit passes the Rule 26 inventory —
the unit's container running and ready; `tini` as pid 1 and one root
supervisor whose two children are `mariadbd` as the engine uid and the
application as the unit uid; nothing the supervisor started running as root;
`mariadbd --no-defaults --skip-networking --socket=/run/<slug>/mysqld.sock`,
`@@skip_networking = 1`, no listening TCP socket among its own file
descriptors and none in `ss`; nothing mounted on `/run/<slug>`; exactly root
(`unix_socket` alone), a locked `mariadb.sys` and the unit's account; DML-only
grants; the exact schema version; the password file's mode, owner and
directory; DML allowed, DDL and the system database refused to the unit's
account; root and the engine's OS account refused to the unit's uid; another
unit's credential refused; the data, socket, password and administrative paths
and all their ancestors not writable by the unit's uid; the datadir not
listable and `mariadbd` not signalable by it — and each unit proves one real
effect read back from its database through the root path.

Each unit's identity is in the same inventory: `etc/identity/` mounted
read-only, the universe UUID in its environment, the pin root-owned and equal
to the parent's derivation, the bootstrap a `0600` file of the unit's account
and never a value in its environment, exactly its declared grants in Vault,
its current incarnation live in Vault (read from `vault.unit_identities` by the
root path), and no evidence owed to Logger for more than 15 minutes. After the
effects, each holder holds a credential Vault issued to its current
incarnation once it owed evidence (an idle unit asks for none). Among the
effects: an anonymous ingest refused by Logger (401); anonymous enqueue, read
and claim refused by Queue and anonymous reads and registrations by Maestro
(401), their open health minimal; the proof writing as `proof` and refused
another unit's events (403); each Queue job claimed, run under one attempt
that ends with its receipt, a late `FAILED` under that attempt refused (409
`STALE_ATTEMPT`) and the identical completion answered the same receipt;
Maestro reaching Queue under its own `queue` credential; the read-back of the
proof's secret leaving `SECRET_READ` evidence with an opaque resource (never
the path or the value) and the anonymous read counted in a
`VAULT_REFUSALS_AGGREGATED` row; and the evidence of the proof's own Vault
write, Queue jobs and Maestro occurrence found receipted in each unit's outbox
and held by Logger under that unit's name — both read from the databases,
never from either unit's answer. The proof calls Logger, Queue and Maestro
under credentials Vault issues to its own identity for each call (one root-only
header file per call, removed after it), and the Vault API with the
construction path's token, read by root from the store; no credential is ever
on a command line.

The secrets are in the same inventory ([secret files](#secret-files)), checked
without printing a value: a root-only list of every secret value the
universe holds — the store's sources, the master key, every bootstrap (the
units' and the proof's) and every unit's MariaDB password — is matched as
fixed strings against each unit's whole `podman inspect` document
(environment, command, labels, mounts, create command) and against the argv
and initial environment of PID 1 and of every process in the unit's pid
namespace, read from the host's `/proc` (at least the four processes of a
unit read, none holding a value; an unreadable one fails). Each secret a
unit consumes is checked delivered — the reference and no value in its
environment, its own copy mounted alone and read-only, inside a `0400` file
of its account with the source's digest — and refused to the engine account
and to `nobody`; no directory of the store or of `etc/vault/` is mounted; the
store itself is root's alone with protected ancestors.

A green health endpoint is not in that list as a proof: it shows a process is
up, never that work happened.

<a id="lifecycle"></a>
## Restart, recreation, and the order of the two processes

`deploy/lifecycle-drill.sh` writes a marker through the Vault, Logger and Queue
APIs, records every table's row count and each password file's digest, then
restarts every unit, checks that `podman-up.sh --preflight` and a plain re-run
keep every container, incarnation and epoch, and recreates the universe
(`podman-up.sh --recreate all` replaces every container). After each: the markers are unchanged in the databases, no table
lost a row, every password file is the same; each unit's log shows the
application stopped before MariaDB and MariaDB shut down cleanly, no crash
recovery, then MariaDB ready, the password kept and the schema retained before
the application started. After the recreation, each unit that holds a
credential runs a new random incarnation — the one Vault now holds for it —
and Vault has issued it a credential once it owed evidence; a credential
issued before the recreation is refused by Logger, one issued after is
accepted.

<a id="restore"></a>
## Restore into a fresh volume

`deploy/restore-drill.sh`, for each unit: a `mariadb-dump --single-transaction
--databases <slug>` through the root path into `sav/dumps/` (root-only), kept
only when the live tables are identical before and after it (the units renew
credentials and relay evidence by themselves, so even a quiet universe writes);
a
throwaway container from the live unit's own image over fresh volumes, started
with `UNIT_RESTORE_DUMP` and `UNIT_MODE=database` — the unit births a new
datadir, loads the dump as root, checks the exact schema version and creates
its account with a new password; the restored tables compared with the live
ones; then the same volumes served by the unit's own application on a drill
port, which reads a control record back through its API (the Vault decrypts a
controlled secret with the universe's key, and refuses another key). A
throwaway unit gets the live pin and a random bootstrap no Vault registered;
its evidence relay's Logger and Maestro's Queue address an unused port, so
nothing it does writes to the live universe. The restored Logger, Queue and
Maestro check the proof's credential at the live Vault — reads of the
authority; a restored unit with evidence owed asks the live Vault for a
credential its unregistered bootstrap never obtains (refused, counted, retried
after a backoff).

When every step of a unit passed, its kept dump is a verified recovery point:
root records it in the live unit's `recovery_points` (the instant taken before
the dump, its SHA-256). Only then may that unit's hourly cleanup remove
delivered, receipted evidence older than 30 days that the point holds
(DECISIONS-20261011 §C; the manifest's `dataLifecycle` declares every class).

The same mechanism restores a unit for real: stop its container, move its
`sav/` aside (kept), put the dump at `sav/restore/<slug>.sql` (root, `0600`) in
an empty `sav/`, and run `podman-up.sh` once with
`RESTORE_DUMP_<slug>=/apps/<slug>/sav/restore/<slug>.sql`; unset it afterwards
(a restore dump is refused by a datadir that already holds a database).

<a id="rehearsal"></a>
## Rehearsal where podman cannot run

`test/rehearsal/rehearsal.live.mjs` runs the real `deploy/podman-up.sh` and the
effects section of `deploy/proof.sh` on a workstation without podman: a fake
podman (`test/rehearsal/bin/podman`) starts each unit's real `server.js` as a
process, its container paths redirected, its database on one throwaway MariaDB
that pkg-db's live runner provisions. It checks the birth order, the
registrations Vault holds by digest with each unit's exact grants, the pin and
the bootstraps, that no secret reaches a command line or the output, that an
idle unit asks Vault for no credential, each unit's credential and evidence, a
re-run and `--preflight` keeping every container, incarnation and epoch,
`--recreate <slug>` recreating that unit alone, the bootstrap renewal (+30 days,
nothing restarted; a tampered record halts it), a recreation's new
incarnations (the old credential refused), the refusal of a changed universe
identity, and the effects section green twice. It proves
nothing about the container shape — one process per unit, one uid for all, no
supervisor, no Rule 26 inventory — and never qualifies the universe: the proof
above, on a real podman, does.

<a id="migration"></a>
## Migration from the separate-database shape

The first materialisation (24 September 2026) ran each unit's MariaDB as a
separate `<universe>-ctr-<slug>-mariadb` container, from the official MariaDB
image; the 10 October 2026 direction forbids that shape. Its datadirs belong to
that image's `mysql` uid, not to the unit image's engine uid, and are not
adopted: `podman-up.sh` refuses both the old container and a datadir of another
owner, and no recursive `chown` is ever made. Per unit, in bootOrder:

1. dump the old database through its own root path
   (`podman exec <universe>-ctr-<slug>-mariadb mariadb-dump -uroot --single-transaction --routines --triggers --databases <slug>`);
2. stop and remove both old containers; move `/apps/<slug>/sav/mariadb` and the
   old `nosav/run/mysqld` aside (kept until the new unit is qualified);
3. place the dump as described under [restore](#restore) and run
   `podman-up.sh` with `RESTORE_DUMP_<slug>`; the existing passwd file is
   reused if it is still in `/apps/<slug>/etc/mysql/localhost/` and owned by
   the unit's uid, otherwise a new one is generated for the fresh datadir;
4. run `proof.sh`, `lifecycle-drill.sh` and `restore-drill.sh`.

The Vault keeps its master key file; its restored `vault_identity` row checks
it at start.

The separate-database shape named Maestro's universe by its instance slug
(`SHAPER_UNIVERSE_ID=<universe>`); the units now require a UUID. Occurrence
ids recorded under the slug stay as they are, and the schedules' next instants
get ids under the UUID: name `SHAPER_UNIVERSE_ID` at the migration and expect
no deduplication between an occurrence recorded before and one after. The
schema version of Vault, Queue and Maestro is now 2 (the evidence outbox,
Vault's unit identities): a dump of a version-1 database is refused by the new
image (exit 7) and needs its own authorized migration (Rule 30).

<a id="image-lock"></a>
## Images

`cfg-image-lock.json` names one immutable digest per brick the manifest
declares, filled from the registry's answer to `podman push --digestfile`. Each
unit image carries its own MariaDB server; there is no separate MariaDB image
to pin. `podman-up.sh` refuses an image whose `org.shaper.unit.*` labels do not
match the manifest. A DEV instance may run from a freshly published tag
(`SHAPER_REGISTRY` + `SHAPER_IMAGE_TAG`), or from images built on its own
machine with `SHAPER_PUSH=0` (`SHAPER_REGISTRY=localhost`); a TEST or PROD one
may not.

<a id="gaps"></a>
## What this universe does not yet do

Recorded so nobody reads the floor as the full target contract of the units
(`operator-deliverables/*-FUNCTIONAL-UNIT-TARGET-2026-09-22.md`):

- Vault's generic secret API keeps its bearer token (Rule 0K); Logger, Queue,
  Maestro and Vault's identity endpoints check Vault-signed credentials;
- root reads every secret file and every process's environment: the files
  close the secrets to the other accounts and to podman's records, not to an
  authorized administrator;
- the bootstrap renewal is installed by `install-renewal-timer.sh`, a separate
  step after `podman-up.sh`;
- refusal counts not yet committed (at most one minute) are lost with Vault's
  process;
- a blocked identity is never repaired by the renewal: it expires unless the
  operator re-registers it (`podman-up.sh --recreate <slug>`); the renewal
  only renews the consistent ones and alerts (decision L);
- the watcher that carries the renewal's alert to a human belongs to the
  universe that installs this base (the Clinic kit's `watch.py`, `ALERT_TO`);
  univ-minimal alone declares no alerting channel, so it stays DEV (Rule 27);
- `recovery_points` is written by the administrative path by convention only:
  the application account's grants (`SELECT, INSERT, UPDATE, DELETE` on its
  database) cover it, so a faulty application could record a point that no
  dump holds and let its own cleanup remove receipted evidence early;
- no Logger cross-event chain or external checkpoint;
- no Queue leases (renewal, expiry) over the durable attempts, and no dead
  letter; no Maestro scheduler leases;
- no automated partition maintenance, off-host encrypted recovery points or
  R2 layout (Rule 16 level 5); dumps are taken by the drill, not on a schedule;
- the MariaDB engine version inside each image follows the Alpine release of
  the Node image and is not pinned by this tree;
- the Vault master key and the database backup live in the same universe
  container, so a container-level backup carries both (Rule 12 gap).
